-2.  
Java에서 volatile로 선언된 int count에 대해 여러 스레드가 count++를 동시에 수행.  
모든 스레드의 작업이 끝났을 때 정확한 결과가 보장되는가? 이유를 작성하시오.  

아니다. Volatile은 멀티스레드 환경에서 각 레지스터가 아닌 메인 메모리  
기준으로 수행되나, 원자성을 보장하지 않는다. 동일한 값을 동시에 읽어서, 이를  
동시에 count를 하면 +=2가 아닌 +=1 되는 결과를 낼 수 있다(Lost Update 발생).

-4. 분산 시스템

사용자가 다시 요청할 경우 중복 결제를 막기 위해 서버는 어떤 방식을 적용할 수 있는가?

멱등성 키(Idempotency Key): 이를 사용하여 하나의 논리적 작업을

동시성 제어: 여러 서버가 동일한 요청을 처리하지 못하도록  
DB의 Unique 제약조건과 원자적 연산 활용.  

외부 PG사 일 때: 결제 성공 후 응답이 유실 가능성이 있으므로,  
PG사의 멱등성 기능 등 조회를 활용.

방식으로 해결할 수 있다.

**개념 학습하기**  
멱등성(Idempotency: 거듭해도 변함없다)  
가장 쉬운 수학적 예시 => 어떤 숫자에 ×1를 수행해도 결과는 언제나 같다.  

HTTP 기준으로 봤을 때? => 같은 요청을 여러 번 보낼때와 1회성과 차이가 있는지.  
예시_1: PUT /account/1 .. 잔액을 5,000원으로 설정  
1번 요청, 2번 요청, .. 3번 이어도, 최종 잔액은 5천원으로 변동 없음: 멱등성 존재  
예시_2: POST /account/1/withdraw .. 1,000원 출금  
요청할 때마다 천 원씩 송금=상태가 달라지므로: 멱등성 없음  
<br>

*멱등성이 왜 중요한가?*  
현실의 서버에서는 정확히 한 번만 처리하도록 보장이 어렵기 때문.  
특히, 요청이 성공했는지 모른다면? => 더 보내야 할 지 않을 지 모름.  

그래서?.. 요청마다 고유한 키(Idempotency Key:)를 보냄 => 중복 실행을 방지를 위해.  
예: 첫 번째 송금 => 실행 .. 첫 번째 송금 재시도 => 중복 실행 방지  
요청 마다 새로운 키를 만드는 것이 아닌 **하나의 논리적인 작업**에 하나의 키 부여.  
<br>

*멱등성의 한계: 동시성*  
먼저 동시에 요청 왔다는 것은, 기계의 시간 단위로 볼 필요가 있다.  
물리적으로 시간은 무한정 단위를 쪼갤 수 있으니, 동시에 온다는 것은 엄밀히 불가능.  

아무튼, (기계 시간 상) 동시에 왔다고 가정할 경우,  
```
서버 A: 키 조회 → 없음 ───────→ 키 생성
서버 B: ──→ 키 조회 → 없음 ───→ 키 생성
```
A, B 두 서버가 모두 자신이 "최초 요청"이라고 판단 가능: 경쟁 상태(Race Condition)  
그럼 어떻게? DB의 unique 기능 활용:  
```
CREATE TABLE payment_requests (
    idempotency_key VARCHAR(100) UNIQUE
);
```
결재 => 결제 테이블에 insert => 성공 시, accounts의 밸런스 조정  
이 것을 하나의 트랜잭션으로 묶어서 **원자성을 보장**하고,  
unique의 키가 하나만 들어가도록 하여, 요청이 묶여서 하나로 기능하도록 할 수 있다.  
<br>
<br>

또 다른 "동시성" 문제_1  
TOCTOU(Time-Of-Check to Time-Of-Use) => 검사 시점과 사용 시점이 다름  

해결 방법_1. 원자적 연산(연산을 중간 개입 없이 실행):  
보통 원자적 연산(검사와 사용 단계를 하나로 묶어서)을 처리한다.  
DB에서 => 구문 내에 검사 조건을 삽입(구문 하나가 하나의 트랜잭션?)  
서버에서 => Java: AtomicInteger 사용  
Redis => Lua Script 사용  

해결 방법_2. 락(다른 작업의 접근을 잠금으로 제한):  
비관적 락 => 데이터를 읽을 때부터 잠금을 걸어 수정을 막는다.  
낙관적 락 => 기본적으로 잠금을 하지 않되, 수정 시 변경 유무 확인(사후 감지)  

해결 방법_3. 직렬화(여러 요청을 순차적으로 처리):  
보통 작업 큐에 넣어서 직렬 처리를 한다.. 작업 a완료 => 작업 b 시작  
<br>

이는 Memory Visibility(공유 변수 가시성)이라고 하는데, 읽기/쓰기 연산이 각 CPU의  
캐시가 아닌 Main Memory에서 직접 이루어짐. 다만, 원자성을 보장하진 x.

복합 인덱스(index)에 대해  
이미 개념은 대략적으로 알고 있음. 다만 복합은 무엇인가?  
```
-- A
CREATE INDEX idx_a ON orders (user_id, created_at DESC);

-- B
CREATE INDEX idx_b ON orders (created_at DESC, user_id);
```
요 둘의 차이? ..  
A: user_id 별로 묶인 상태에서 생성일 순으로 정렬  
B: 생성일 순으로 정렬하고, 생성일 동일 시 user_id 기준으로 정렬  

인덱스는 DESC ASC 각각 기준으로 생성이 가능하다: 실제 물리적으로는 다르다.  
그러나.. B+Tree 기준으로, DESC 생성 => ASC 역방향 탐색이 가능하다.  
<br>

*복합 키 정렬*  
복합 키 정렬은 비교적 단순하다. 두 개의 속성을 하나의 키로 삼아 하나의 B+Tree 생성.  
예를 들어 다음과 같은 Indext 생성을 가정해보자:  
```
CREATE INDEX idx_a
ON orders (user_id ASC, updated_at ASC);
```
이렇게 생성할 경우, B+Tree의 Leaf Node는 논리적으로 다음 순으로 배치된다:  
```
user_id  updated_at
────────────────────
10       10월 20일
10       10월 24일
10       10월 28일
20       10월 21일
20       10월 25일
20       10월 27일
30       10월 22일
30       10월 26일
```
WHERE user_id = 20 ORDER BY updated_at ASC; => 20번을 찾고 순서대로 읽으면 됨.    
WHERE updated_at >= '2026-10-25' ORDER BY user_id; => 연속 범위가 아님.  

일반적으로 후자의 경우 탐색이 더 느려질 가능성이 높다.  
각각 O(log N + K), O(N)로 추정.

트랜잭션 격리(Isolation)에 대해:  
ACID(Atomicity/Consistency/Isolation/Durability)에 들어 봤나? 이 중 하나.  
트랜잭션 수행 시 다른 트랜잭션의 연산이 끼어들지 못하게 하는 것.  
격리 수준은 통상 4개로 나눠지며, 가장 낮은 순 부터 설멸하자면:  

-1. Uncommitted Read:  
다른 트랜잭션에서 커밋되지 않은 데이터에 접근 가능,  
예: 박기영 => 우기영, 으로 변경 후 commit시..  
타 트랜잭션에서 중간에 변경 후 완료 안된 우기영을 select하여 조회 가능.  
만약 변경 트랜잭션이 중간에 오류가 생겨 rollback시, "데이터 부적합"이 생길 수 있다.  
커밋되지 않은 트랜잭션에 접근하여 데이터를 읽는 것을 **Dirty Read**라 한다.  

-2. Committed Read:  
이름에서 유추하듯, 커밋된 데이터로만 접근할 수 있는 격리 수준.  
```
시간 →
A: UPDATE('우기영') ───────── COMMIT
B:      SELECT FOR UPDATE ──대기──→ '박기영' 조회
```
이와 같은 방식으로 진행되는데, A가 실행한다고 B가 Lock마냥 대기하는 것이 아니라,  
Undo Area에서 커밋 이전 값을 읽어온다.  

-3. Repeatable Read:  
Non Repeatable Read(반복해도 동일 결과 보장 못함)문제를 해결하기 위한 격리 수준.   
Non Repeatable Read에 대해 짧게 설명하자면.. 하나의 트랜잭션에서 두 번 SELECT가  
실행, 중간에 다른 트랜잭션이 UPDATE하여 변동된 값을 읽음. 아래 예시:  
```
A: BEGIN ── SELECT ─────────── SELECT ── COMMIT
               ↓                  ↓
            100만원              50만원

B:          BEGIN ── UPDATE ── COMMIT
                         ↓
                      50만원
```
이를 해결하기 위해, 커밋된 데이터만 읽을 수 있는.. 정확히는,  
트랜잭션마다 ID가 있고, 일치하는 버전만 읽을 수 있다.  
MVCC(Multi Version Concurrency Control)이라 해가지고, Undo Area를 다른 버전  
처럼 관리를 하고, 이 버전을 읽는 것이다.   
=> 즉, 새로운 값으로 변경해도, 해당 트랜잭션의 Read View에 맞는 Log를 찾아 읽는다.  

-4. Serializable:  
가장 고수준 격리수준. 트랜잭션을 무조건 순차적으로 진행시킴. Lock을 사용하게 되는데,  
SELECT의 경우 Shared Lock이 걸리고, UPDATE, DELETE, INSERT은 Exclusive Lock  
을 씀.  
<br>
<br>

Cache Stampede 도식화 하기..  
```
캐시: 존재 ── TTL 만료 ───────── 재생성 완료 ── 존재
                    │                  │
요청 A:             ├── DB 조회 ── 캐시 저장
요청 B:             ├── DB 조회
요청 C:             ├── DB 조회
요청 D:             └── DB 조회
                                       │
                          이후 요청은 캐시 이용
```
캐시를 다시 생성하는데 200ms가 걸린다고 가정하자. 근데 이 시간에도 약 1만개의  
요청이 오고, 이 중 2천개가 캐시 미스를 겪는다.. 일종의 동시성 문제. 해결책은:  
Singleflight => 한 요청만 DB 조회해 캐시 생성, 나머지는 대기  
분산 락 => Redis에 락을 건 다음, 다음과 같은 흐름을 만든다:  
```
요청 A: 캐시 미스 → 락 획득 → DB 조회 → 캐시 저장 → 락 해제
요청 B: 캐시 미스 → 락 실패 ─────────────→ 캐시 조회
요청 C: 캐시 미스 → 락 실패 ─────────────→ 캐시 조회
```
여기서 B, C도 캐시 미스를 확인하지만 락 획득에 실패하고, 서버 로직에 따라  
대기하다가, 생성된 캐시를 얻는다(자동 요청이 아니라 서버에서 구현 필요).  
<br>
<br>

Spring의 @Transactional은..  
먼저 자가 호출(self-invocation)에 대해 설명하자면 다음 아래와 같다:  
```
@Service
public class PaymentService {

    public void process() {
        this.pay();
    }

    @Transactional
    public void pay() {
        // DB 작업
    }
}
```
이렇게 this.pay라는 방식으로 아래 Transactional이 박힌 메서드를 "자가"호출을 한다.  

프록시 패턴은 일반적인 객체지향 설계 개념이고, Spring만의 기능이 아님.  
Spring에서는 @Transactional이 기능하려면 프록세 패턴을 사용해야 하고, 이가 강제됨
