#### DB·트랜잭션  

**문제 01**  
> 동시성 문제이다. 하나의 트랜잭션이 SELECT => UPDATE 일 경우,  
> MySQL InnoDB 기본 격리수준에서 해결책  

여기서 두 건 => 동시성 문제를 추론할 수 있다.. 기본 격리수준: Repeatable Read이다.  
"주관식 1"에서 기술한 내용과 마찬가지로 MVCC와 Read View가 버전별로 존재한다. 근데 동시성 문제?  

말이 어렵다: 
*MVCC가 트랜잭션마다 읽을 버전을 구분하지만,*   
*그 버전을 기준으로 수행한 수정 작업까지 서로 격리해서 독립적으로 저장해 주지는 않기 때문*  

문제를 도식화 하면 다음과 같다:  
먼저, 10만원 잔고가 있고 -7만원 하는 두 개의 트랜잭션 A/B가 존재한다고 가정해보자,  
```
시간     트랜잭션 A               트랜잭션 B
───────────────────────────────────────────
0ms      BEGIN

1ms      UPDATE 잔액 = 3만
         (아직 COMMIT 안 함)

2ms                               BEGIN
3ms                               SELECT
                                  → Read View 생성(트랜잭션이 이 초창기 버전?에 머뭄)
                                  → A는 미커밋 상태
                                  → 10만 원 조회

4ms      COMMIT

5ms                               SELECT
                                  → 기존 Read View 사용
                                  → 여전히 10만 원

                                  → UPDATE 잔액 = 3만
6ms                               COMMIT
```
Read View는 커밋된 버전을 기준으로 생성이 된다. 트랜잭션 B는 이미 A가 -7 = 3만원 도중 임에도  
구형 Read View(10만원)을 사용하여 동시성 문제가 발생하게 된다. 이를 전문 용어로   
**Lost update**라고, 이미 <u>낡은 읽기</u>를 한다고 함.  
<br>

해결 방법으로는..  
-1. 무식하게 "직렬화(계좌 단위)"로 할 수 있다. 어쨌든 순차적으로 처리하면 되니까,  
다만, 속도 등에서 부작용 발생 가능. 

-2. 조건부 원자 UPDATE.. 기본적으로 단일 update sql 구문 하나는 "원자적"으로 실행이 된다.  
DB의 행 장금(x Lock)을 하기 때문. 예시 코드로는:  
```
UPDATE account
SET balance = balance - 70000
WHERE id = 1 AND balance >= 70000;
```
로, set으로 미리 -7만원을 한 다음 where로 검사?를 하는 것이다. 
`AND balance >= 70000`에서 조건을 만족하지 못하면 `SET`까지 무효화가 됨.   

-3. 락을 사용해도 된다. 비관적(일단 잠금)/낙관적(하고 나서 확인) 락 모두 가능.  
비관적 락은 `SELECT * .. FOR UPDATE;` 식으로 하여, Select 시작 구문이 락이 걸려 있으면  
진입 자체를 못하게 한다. 동시에 처리를 못하니 사실상 "순차 처리"가 이뤄진다.  
낙관적 락은 Entity(Spring 기준)에 `@Version`를 선언, 버전이 변경되었을 경우 rollback을 한다.

**문제 07**  
> 데드락 문제이다.  
> 데드락 발생 조건을 논리적으로 분해한 4가지를 기술하고 해결책이 필요.   

먼저 **교착 상태(Dead Lock)**에 대한 이해가 필요하다. 트랜잭션 기반해서 설명:  
-. 트랜잭션 A: 테이블 1 업데이트 후 => 테이블 2 업데이트 하려고 함(2번 락 대기)    
-. 트랜잭션 B: 테이블 2 업데이트 후 => 테이블 1 업데이트 하려고 함(1번 락 대기)  
이 상황에서 모두가 기다리고 있는 교착 상태.. 보통 이를 정의하자면,  
*두 개 이상의 트랜잭션이 서로가 점유하고 있는 자원을 획득하기 위해 무한정 대기 상태*라 함  

이걸 세부적으로 <u>4 필요조건</u>으로 설명이 가능한데(논리적으로 분해 한 것),  
1. 상호 배제: 하나의 자원을 동시에 사용 x => Lock을 동시에 가질 수 없음  
2. 점유와 대기: 이미 자원 점유 상태에서 타 자원 기다림 => A/B가 각각 이미 락을 보유  
3. 비선점: 강제로 빼앗을 수 없음 => 가진 Lock을 누군가 뺐을 수 없음, 놓을 때 까지 대기  
4. 순환 대기: 서로 상대방이 가진 것을 기다림 => A/B가 서로 노리고 있는 구조  

그럼 문제 07번의 "A→B 이체와 B→A 이체"에서 어떻게 데드락이 걸렸는지 설명 할 수 있을까?  
이체를 하려면 A 테이블을 Select하고 => Update하고(여기서 A 테이블 행 Lock).. 이후 B 테이블로 감  
또 다른 이체는 B 테이블 Select => Update(B 테이블 행 Lock) 이후 A 테이블로 가야 함.  
서로 Lock을 하고 있고, 상대의 Lock을 기다리고 있는 상황.  
<br>

어플리케이션 수준의 해결책?  
```
시간     트랜잭션 T1 (A → B)      트랜잭션 T2 (B → A)
────────────────────────────────────────────────────
1ms      A Lock 획득
2ms                               B Lock 획득
3ms      B Lock 요청 → 대기
4ms                               A Lock 요청 → 대기

결과: 서로 기다리는 데드락 발생



시간     트랜잭션 T1 (A → B)      트랜잭션 T2 (B → A)
────────────────────────────────────────────────────
1ms      A Lock 획득
2ms                               A Lock 요청 → 대기
3ms      B Lock 획득
4ms      이체 처리
5ms      COMMIT → 락 해제
6ms                               A Lock 획득
7ms                               B Lock 획득
8ms                               이체 처리 → COMMIT

결과: 순환 대기 없이 순차적으로 처리
```
T2는 B의 락 부터 먼저 가져도 되지만, 순서에 맞춰 A락을 획득해야 진행이 되도록 강제한다. 즉,  
<u>트랜잭션이 처리하는 논리적 순서와 관계 없이, 필요한 락을 미리 정해둔 순서로 획득하도록 강제</u>  
하는 것이다.

**문제 16**  
> Dirty read, Non-repeatable read, Phantom read 설명 요구.  
> InnoDB 기준 REPEATABLE READ 설정에서 Phantom read는 어떻게 처리되는지 이해 필요.  

각각 read 개념에 대해 짧게 훑어(복습해)보자  
-. Dirty read: 커밋되지 않은 값을 읽는 것 => READ UNCOMMITTED 설정에서 가능  
-. Non-repeatable read: 중간에 변경(commit)된 값을 읽음 => READ COMMITTED 설정에서 가능    
-. Repeatable read: non~ 못하게 동일 뷰 읽음 => REPEATABLE READ(기본값)  
-. Phantom read: 다른 트랜잭션이 삽입된 row를 "중간에" 읽음, 아래 예시:  
```
시간     트랜잭션 A                  트랜잭션 B
────────────────────────────────────────────────
1ms      BEGIN                       BEGIN

2ms      SELECT WHERE age >= 20
         → 10명 조회

3ms                                  INSERT (age=25)

4ms                                  COMMIT

5ms      SELECT WHERE age >= 20
         → 11명 조회
         → Phantom Read 발생
```

InnoDB의 REPEATABLE READ에서는?.. Read View가 이전 것을 읽도록 고정되기 때문에..  
새 행이 끼어들어도 이전 결과를 보도록 함.

#### Kafka·메시징 

**문제 03**  
> Kafka로 발행 시, 메시지의 순서 보장 여부 이해 필요.  
> Kafka 구조(토픽, 파티션, 오프셋)을 이해하고 서비스 요구사항을 도출해야 함.  

메시지 키로 무엇을 쓰고, 그래도 순서가 깨질 수 있는 경우를 두 가지 이상 쓰세요. 

먼저 Producer(주문 서비스)에서 주문을 생성하고 카프카로 보낸다고 가정을 해보자:  
```
주문 서비스 (Producer)
        │
        │ 주문 이벤트 발행
        ▼
    Kafka
        │
        ▼
  Topic: orders
        │
        ├── Partition 0
        │     ├─ 주문 A
        │     ├─ 주문 D
        │     └─ 주문 G
        │
        └── Partition 1
              ├─ 주문 C
              └─ 주문 F
```
Topic: orders라는 종류의 메시지를 모아놓는 "논리적" 공간  
Partition: Topic의 메시지를 실제 나누어 저장하는 "단위"  
Offset: 각 파티션 안에 메시지의 위치를 나타내는 정보  

굳이 Topic 하나에 파티션을 나눈 이유? => 병렬처리: 동시에 여러 개 처리 가능  
다만, 하나의 파티션에서만 **순서를 보장**한다. 파티션 간의 순서는 보장 못함.  
따라서, 위 질문에서 계좌 내부에서의 순서를 반드시 보장해야 한다면? => account_id 기반 파티션 분배  
<br>

그래도 순서가 깨지는 경우가 있다고..?  
케이스 1: 멱등 프로듀서 없이 재시도 할 때:  
```
주문 서비스(Producer)             Kafka Partition 0
──────────────────────────────────────────────────
1ms   주문 A 전송 ────────────→ 전송 실패

2ms   주문 B 전송 ────────────→ 저장 성공
                                Offset 0: B

3ms   주문 A 재전송 ──────────→ 저장 성공
                                Offset 1: A
```
원래 순서가 아닌 B => A 역순으로 카프카 파티션에 쌓이게 된다.  
`enable.idempotence=true`사용하면 된다던데.. 자세한 내용은 스킵.  

케이스 2: 파티션 수를 늘렸을 경우:  
동일 키의 메시지가 다른 파티션으로 넘어갈 수 있다. 파티션 간의 순서는 보장 안하니 문제.  

추가로, 컨슈머 단계에서, 이 녀석이 멀티 스레드로 병렬로 순서 없이 처리하면 문제가 생긴다.

**문제 04**  
> 메시지를 받는 Consumer가 죽었을 경우를 가정.  
> Consumer 메시지 처리 관련 Kafka 정책 이해가 필요.  
> 시나리오를 가정하고, 해결책 도출할 것.  

카프카 메시지는 consumer가 "읽었다고" 삭제되지 않음: 별도 삭제 정책이 존재.  
대신 Offset으로 consumer가 어디까지 읽었는지 기록하는 구조.  
Offset은 어떻게 갱신되나? => Consumer가 커밋 요청을 보내야 함(얘가 죽으면 문제).  
```
Kafka                           Consumer
─────────────────────────────────────────
Offset 0: A                     처리 완료
Offset 1: B                     처리 완료
Offset 2: C                     처리 완료
Offset 3: D                     미처리
Offset 4: E                     미처리
```
<br>

카프카는 세 가지 메시지 처리 방식이 있다:  
| 방식 | 처리 순서 | 결과 |
| :-- | :-- | :-- |
|At-most-once | 오프셋 커밋 → 메시지 처리 | 메시지 유실 가능, 중복 방지 |
|At-least-once | 메시지 처리 → 오프셋 커밋 | 중복 처리 가능, 유실 방지 |
|Exactly-once | 처리 결과와 소비 위치를 원자적으로 확정 | 조건이 충족되면 중복 효과와 유실 방지 | 

Consumer가 처리 후 "처리 완료!" 커밋을 보내는 것은 At-least-once 이다.  
금융 환경에서는 유실 자체가 치명적이기 때문에, 중복 전달을 고려해도 이를 선택할 필요성 있음.  
대신, Consumer 쪽에서 **멱등성 처리**를 하는 방식으로 개선 필요.  
어떻게? => event_id 같은 걸로 별도 테이블 만들어서, 중복 처리 못하도록(unique) 설정.

**문제 05**  
> Consumer가 아닌 Producer에서 문제 발생 가정.  
> @Transactional => 하나의 트랜잭션에서 메시지를 send()할 경우.  
> 문제 발생 시나리오 2가지를 가정하고 대안 생각하기.  

메서드에서 `save()`를 했다고 commit되지 않는다. DB에 insert등이 된 상황.  
`@Transactional`내의 메서드가 끝나야 자동으로 commit, 확정이 진행.  

만약 카프카 send 후 => DB COMMIT을 할 경우 흐름은 이렇다:  
```
                  1ms           2ms            3ms             4ms
                   │             │              │               │
Producer      주문 A 요청 ──── DB INSERT ──── Kafka SEND ──── DB COMMIT 요청
                                 │              │               │
DB                               ▼              │               ▼
                             임시 저장 ────────────────→ ROLLBACK
                                                │
Kafka                                           ▼
                                           이벤트 저장 성공

결과: DB에 주문 A 없음 / Kafka에 주문 A 이벤트 존재
```
이렇게 할 경우, 오류가 생겨 roll back으로 DB는 원상복구 => 메시지는 전송 "유령 이벤트" 발생.   
순서를 바꿀 경우, 저장은 확정되도 메시지는 전송되지 않는 문제가 발생 가능.  
.. 이 둘을 원자적으로 묶을 수 없기 때문: dual write라고 한다 보통.  
<br>  

해결책들..  
Transactional Outbox: DB 저장과 메시지 저장 불일치 해결위한 "설계 패턴"  
```
시간          1ms       2ms        3ms       4ms       5ms       6ms
               │         │          │         │         │         │
Producer    주문 요청 ── INSERT ── COMMIT ── !!사망!!
                         │          │
DB                       ▼          ▼
                      주문 저장   주문+Outbox
                      Outbox 저장   확정
                                                 │
작업자                                        Outbox 조회 ── SEND
                                                             │
Kafka                                                        ▼
                                                          이벤트 저장

결과: 장애 후에도 Outbox 기록을 통해 Kafka 발행 재시도 가능
```
설계 패턴이니까, 특별히 도구가 있는게 아니고 설계를 해야 한다.  
별도의 Message를 저장하는 테이블을 만들고, COMMIT 분기를 여러 개(트랜잭션 여러 개)를 설정.  

만약 중간에 죽었을 경우?  
**DB COMMIT 전 사망**: 주문과 Outbox 기록이 함께 롤백됨.  
**DB COMMIT 후 사망**: 주문과 Outbox 기록이 남아 있으므로 나중에 Kafka 발행 가능.  
**Kafka 발행 후 사망**: 발행 완료 표시 전에 죽었다면 재발행 가능 =>Consumer의 멱등 처리.

**문제 17**  
> Kafka 클러스터를 옮기는 것을 가정 => 발생하는 문제에 대해 기술  
> 오프셋 변환 시 "유실"과 "중복" 개념 이해 필요.  

Kafka 클러스터를 옮긴 다는 것은 새롭게 설치하고 그러는 것이 아니라, 다른 Kafka 쪽에 옮기는 것.  
```
                데이터센터 A             데이터센터 B
                (기존 Kafka)            (대체 Kafka)
───────────────────────────────────────────────────────
주문 A          Offset 100              Offset 80
주문 B          Offset 101              Offset 81
주문 C          Offset 102              Offset 82
주문 D          Offset 103              Offset 83

Consumer       Offset 102 커밋          아직 없음
```
만약 A의 Offset 102를 B에 그대로 적용하면? => 80~ 번 들이 전부 유실되는 문제가 나타난다.  
그럼 해결은 어떻게? => 오프셋 매핑(103 => 82)로 옮기거나, Timestamp을 기준으로 B의 읽을 위치를  
검색하여 넣음.  

오프셋 변환: 읽은 지점 갱신.. 만약 상황이 offset기준 전-후 중 선택을 해야 할 때..  
금융에선 유실이 치명적이니, "중복"을 선택하고 consumer에서 멱등성 처리하면 됨.
