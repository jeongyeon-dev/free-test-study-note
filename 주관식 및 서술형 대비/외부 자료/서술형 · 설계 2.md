**문제 07**  
> 동시성 문제이다. 100만원 => 70만원 주문 동시에 × 2  
> 주문 => 외부 브로커 => 결과(비동기 응답)  

여기서 **홀드**라는 개념을 익혀야 한다.  
=> 미리 금액을 확보해서 다른 주문에 사용하지 못하도록 "일시적"으로 묶어둠.  

그냥 "조건부 UPDATE"를 사용하지 않고 홀드를 사용하는 이유?  
조건부로 바로 금액 차감 => 외부 브로커(비동기) => 실패: 돈이 사용된 것으로 기록됨.  
따라서.. 다름과 같은 흐름을 거쳐야 함:  
```
사용자 매수 주문
       ↓
서비스 서버 (주문 접수)
       ↓
주문 금액 홀드
       ↓
외부 브로커로 주문 전달
       ↓
체결 대기 (수초~수시간 가능)
       ↓
체결 → 실제 차감
취소·거부 → 홀드 해제
```
<br>

주문 접수: 멱등성(동일한 주문이 반복해서 브로커 전송 못하도록)  
주문 금액 홀드: 조건부 UPDATE  

체결 확정: 조건부 UPDATE + 트랜잭션 + 멱등성(브로커의 재전송 대비).. 이 필요  
응답 없음: 홀드 상태를 유지(외부 브로커가 멱등성 보장한다면 재시도)  
<br>

*홀드와 체결 차감이 제대로 구현되어 있으면, 접수 순서대로 체결될 필요는 없다*  
*조건부 UPDATE 자체가 베타 락을 사용하므로 직렬화 필요성은 없다*  

-- 베타 락: 해당 트랜젝션만 DB(혹은 행)에 독점적으로 수행

**문제 08**  
> 대사(reconciliation) 배치에 대한 이해와 설명 요구.  
> 구체적 시나리오: 장 마감 => 브로커에서 체결 내역 파일(수백만 건) 발송 => 원장과 비교 및 보정  

예시로, 받는 대상이 토스 증권이라 가정할 경우:  
- 보내는 주체: 거래소(KRX) 또는 외부 브로커·청산기관 등 거래를 처리한 외부 기관.  
- 받는 주체: 토스증권.  
- 비교 대상: 외부 기관이 보내준 체결 내역 vs 토스증권 내부 DB에 기록된 체결 내역.  
- 비교 수행: 토스증권의 대사 배치 시스템.  
<br>

**대사 배치 시스템**: 서로 다른 시스템, 데이터 저장소 간 데이터 정합성 검증하는 프로그램.  
금융권에 한정에서 이 설계 패턴?은 제법 정형화 되어 있다. 아래 참고:  
```
1. 파일 수신과 적재
       ↓
2. 대조
       ↓
3. 불일치 분류
       ↓
4. 보정 및 재검증
       ↓
5. 결과 확정 및 감사 기록
```  
<br>

*수신과 적재*  
브로커에서 수신을 하고 임시 테이블을 만들어 적재를 수행한다.  
체크섬(디지털 지문)과 건수, 파일ID를 통해 중복 수신을 방지한다.  
이 단계에서는 "중복 수신"에 대한 검증을 수행한다.  
늦게 도착한 파일 => 다시 루프 돌기 시작..  

*대조*  
큰 단위(계좌/종목별)를 기준으로 합계 등을 먼저 비교한다(비교 비용 줄이기).  
여기서 합계가 다른 계좌는 체결 번호 단위로 상세 비교함.  
말 그대로 대조만 수행하는 단계이다. 여기서 수정이나 피드백은 하지 않음?..  

*불일치 분류*  
우리에게만 있음/상대에게만 있음/값이 다름(건수, 수량 등).. 으로 세부적으로 분류한다.  

*보정 및 재검증*  
가장 위험도가 높은 핵심?과 같은 곳..  
보정 대상 판정 => 보정 실행 => 재검증. 과 같은 흐름을 거친다.  
여기서 "보정 대상 판정"은 원인이 명확한 유형(누락 체결 반영 등)만 자동 보정을 하고,  
나머지는 별도 프로세스.  
=> 멱등성 중요.. 왜? 장애 후 특정 항목의 재실행 방지를 위해.  

*결과 확정 및 기록하기*  
보정이력, 소요시간 등을 기록하고, 결과를 확정.  
<br>

.. 중간에 실패 시 "청크 단위 체크포인트"로 재시작. (단계 체크포인트도 포함) 예시:  
```
1. 파일 수신·검증·적재 → 완료
2. 대조 → 100만 건 중 60만 건 완료
3. 불일치 분류 → 미완료
4. 보정·재검증 → 미완료
5. 결과 확정 → 미완료
```

**문제 09**  
> 캐시 + 장애 대응  
> failover(페일오버: 예비 시스템 가동)에 수십 초 걸림: 공백이 생겼다는 것.  
> 이 수십 초 동안 어떻게 버티게 할 지 + 복구 후 나타나는 문제.. 설계 역량을 물어보는 듯.  

1번 문제 상황: 수십 초의 공백을 어떻게 처리하나?  
일종의 뗌빵 조치를 한다. 전문용어로는 Graceful Degradation(점진적 성능·기능 저하) 패턴.  
왜? => Redis 복구 까지 요청 대기하면 요청이 계속 쌓임. DB에 그냥 전달하면 부하 발생하므로.  

그럼 어떻게 하나?.. 먼저 <u>데이터의 속성에 따른 분류</u>를 한다.  
실시간성이 필수인 데이터(호가 등): 서킷 브레이커로 요청을 빠르게 차단 => 알림 발송(죄송합..)  
일부 지연이 허용 데이터(현재가 등): 로컬 캐시 TTL 등을 늘려서 제공 => 얼마나 지연됬는지 표시  
<br>

2번 문제 상황: 새 Redis 노드가 Primary로 승격되었을 시  
새 Redis는 기존 Redis의 Replica(복제본)이 들어가 있을 수 있음. 그런데 이 데이터는:  
1. 최신 시세가 반영 안되었을 수 있음(정합성)  
2. TTL이 이미 지난 것들이 있어 사라져 있을 수 있음(유실)  

이럴 경우 트래픽이 DB로 집중되는 **캐시 스탬피드(Cach Stampede)**가 발생 가능.  
여기서 워밍 업(Cache Warming)을 하여 새 캐시들을 채워 넣어 사전에 방지.  
<br>

시퀀스 번호 등으로 비동기적으로 오는 데이터(호가 등)을 최신값 반영 형태로 할 필요 있음.

**문제 10**  
> 대량 발송 + 매칭이 섞인 문제이다.  
> 목표가 알림: 초당 수십 번 바뀌는데, 도달했을 시 대규모 사용자들에게 알림 발송해야 함.  
> 중복 + 폭주 + 실패 상황도 시나리오에 포함할 것.  

먼저, "TreeMap" 떠오른다. 최저가(내림차순), 최대가(오름차순) => O(log N + K)이다.  
TreeMap은 <u>범위 검색</u>에 효율적이다. 해당 구간의 목표가들을 다 빠르게 찾을 수 있음(범위 조회)  

TreeMap은 자체가 Map이다:  
```
TreeMap<Integer, List<Alert>> alerts = new TreeMap<>();
```
즉, 안에 List에서 알림 발송 대상자(ex. 사용자 ID) 등을 저장해서 순차적으로 발송을 하면 된다.   
<br>

시세가 지속적으로 변동할 경우:  
목표가가 8만원, 근데 순식간에 8만 => 7만 9990원이 됨: 이미 확정된 총 알림을 (큐)에서 발송    
시세 노이즈(`79,990 → 80,010 → 79,990 → 80,020`): 한 번 발동된 알림(ID)을 비활성화 할 것.  
다만, 이후 알람 신청한 얘들은 보내야 하므로, 알람의 등록 시점을 보관하는 정보가 필요:
```
List<Alert>

class Alert {
    long alertId;
    long userId;
    int targetPrice;
    long registeredSeq; // 등록 당시 마지막으로 처리한 시세 seq
    AlertStatus status;  // ACTIVE, TRIGGERED
}
```
<br>

중복 발송 차단: Worker 쪽에 발송 이력 테이블을 만들고, key는 unique하게 하여 멱등 처리한다.  
발송 폭주 시: 장 시작, 급등락시 동시에 보내야 할 수 있다. *윈도우 같은 걸로 정량적 worker에 넣기.  
발송 실패 시: 스마트폰 알람 인프라는 구글과 애플이 제공한다. 토큰 만료 => 중단, 일시 오류 => 다시  

*푸시 토큰: 특정 기기에 설치된 앱에 보낼 목적지 식별자*    
*DLQ(Dead Letter Queue): 실페한 메시지를 저장하는 큐*
