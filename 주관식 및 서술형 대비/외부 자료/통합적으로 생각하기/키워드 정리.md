**Stateful <=> Stateless**  
JWT 기반 인증: "서버가 이전 요청 기억 필요성 X" => 클라의 JWT에 정보가 있기 때문: Stateless  
세션 기반 인증: "서버가 세션을 저장해야 함" => 세션 아이디 + 서버 세션 정보 조회: Statefull  

Kafka 서버(브로커)는? => Stateful: 상태 정보를 유지해야 하기 때문.  
Consumer 처리 위치: 컨슈머가 어디까지 처리를 했는지 표시 상태 정보.  
복제 상태: 다른 브로커가 어디까지 데이터를 복제했는지 상태 정보.

**멱등성(idempotency)**  
몇 번 반복했다. 동일 요청 중복해도 => 받는 쪽 상태가 1회 이후 변동하지 않는 것.  
보통 **lost update(갱신 손실)**을 방지하기 위해 `at-least-once`방식 채택 => 컨슈머 멱등성  

메시지 큐(Kafka)에서 보장 방식: 컨슈머와 관계    
`at-least-once`: 최소 한번(중복 가능).. 메시지를 먼저 처리 → Offset 커밋  
`at-most-once`: 최대 한번(유실 가능).. Offset을 먼저 커밋 → 메시지 처리  
`exactly-once`: 정확히 한번  

조건부 업데이트 `UPDATE account SET .. WHERE id = 1 AND 조건 기술`  
<br>

**프로듀서 => 카프카**에서의 멱등성 & 원자성  
`enable.idempotence=true` 얘 또 까먹음. 굳이 암기 필요성?   
동일한 메시지 = 동일한 Seq번호, PID. Kafka 쪽에서 식별해 중복 적재 막음.  

프로듀서 측에서 DB에 먼저 Write하고 카프카에 발행하는 경우?  
둘 사이의 원자성으로 묶기 위해 => **Transactional Outbox 패턴**  
=> Outbox에 메시지 발행 기록함: 중간에 재실행 되어도 유실 없이 전송 가능 => Relay가 읽고 행동

MySQL **격리 수준** 정리:  
READ UNCOMMITED: 커밋 안된거 중간에 읽기 => `Dirty Read` 가능   
READ COMMITED: 커밋 된 거만 읽기.. 뷰는 매번 새거 => `Phantom Read` 여기까지 가능    
REPEATABLE READ: 뷰 만들고 변경 안된거 "반복적" 읽기 => 기본 격리 수준  
SERIALIZABLE: 순차적으로 하나하나 되도록 하기

레코드 락(본 행만 잠금), 갭 락(인접 삽입 막음), 넥스트 키 락(레코드 + 갭)

**TCP**관련 정리  
TIME_WAIT <=> CLOSE_WAIT:  
전자: 닫기 요청을 하는 쪽(주로 클라). ACK 패킷 등 유실을 대비해 대기탐. 2MSL 동안    
후자: 수동적 close 하는 측. 닫기 요청 받으면 => CLOSE_WAIT 상태 진입.. 상대 먹통 시 계속 이 상태 

3-way-Handshake: 시작시.. 연결 요청 => 요청 확인/응답 => 응답 확인    
4-way-Handshake: 종료시.. 종료 요청 => 요청 확인 .. 종료 준비 완료 => 종료 확인

**분산 모델에서 일관성 유지**  
Read-your-writes: 내가 쓴 건 바로 읽을 수 있게  
Monotonic Reads: 읽고 다음에 읽은 게 과거 것이 아니도록  
Monotonic Writes: 쓰기 순서가 유지되어야 함  
Writes-follow-reads: 적은 대상의 내용이 과거 것이 아니도록(ex. 게시글 => 댓글)  

이는 분산, 혹은 앞에서 학습한 CQRS(Commend Query Responsibility Segreagation):  
읽기 쓰기 분리 "아키텍처 패턴"에서 나타날 수 있음.
