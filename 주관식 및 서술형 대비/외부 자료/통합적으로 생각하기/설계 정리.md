#### 주식 서비스 아키텍처를 중심으로    

**주식 예약 주문**
주식 예약 주문 100만건 => 이를 개장 시간에 처리해야 한다:  
TPS가 평소 20배 폭증: 외부 브로커(상한 존재)에 전달해야 함  
(유실/이중 방지 + 장애 대응)  

외부 브로커는 제한이 있는 만큼 Rate Limiter(유량 제어)를 해야 함.  
OO윈도우 등 다양하지만, "토큰 버킷"을 사용해서 Capacity 기반해서 전달하는 것이 좋을 듯.  

동시에, 개장: 실시간 주문도 받는 것을 의미함.  
둘 다 동일한 유량 제어를 받을 경우 => 예약이 선점 가능: 배분 필요성 있음.  
그와 별개로 worker를 각각 분리해서 설계 필요성? 굳이 이긴 함: 벌크헤드    
<br>

<u>외부 브로커 응답이 수 초 걸리는 경우</u>에 대비도 해야 함:  
중복 방지 위해: 응답이 느리다고 재전송 하면 안됨 + 주문 별 고유ID로 멱등하게 함  
Producer 부분일 수도 있으니까 Transactional Outbox 사용하여 주문 테이블 저장.  
기다리다가 TIME_OUT => 대사(Reconciliation)를 함: 외부 브로커 체결 내역과 비교  

주문 상태 세분화: 전송 - 처리 - 처리완료(체결됨/실패) - 타임아웃(대사)  

*장애 관련 대응은?*  
정석대로: 실패율 임계치 도달 => 서킷 브레이커 => failover로 대체  
<br>
<br>

**주식 바로 주문**  
해당 주문이 체결/미체결 완료가 될 때까지 "홀드"하는 로직이 구현이 되어야 함.  
홀드는 `조건부 UPDATE`방식으로 해서 마이너스 안나오게 => `Transactional Outbox`로 기록/전송  

홀드 해제 여부는 외부 브로커에서 응답을 통해 결정.  
만약 응답 지연이 임계점을 넘고 + 외부 브로커가 멱등성을 지원하면 재전송 시도.  

체결될 경우, 이중 차감이 안되도록 홀드 금액을 UPDATE함: 외부 브로커 중복 발송 대비  
멱등성 보장인데.. 조건부 UPDATE로는 안되고 체결 ID를 unique 설정을 통해 가능.  
<br>
<br>

**목표가 알림**  
Java로 구현할 경우 TreeMap을 사용한다.  
최저가, 최대가 순으로 정렬을 하고 이의 시간복잡도는 O(log N + K)  
목표가에 도달했다면 해당되는 유저 ID등 기반으로 하여 모두 전송을 한다.  
또한 목표가에 반복적으로 도달(시세 노이즈)을 하여 중복 발송할 수 있으니, 알람 ID 기반 중복 차단  

발송을 보내는 Worker를 설계하고 알림 ID를 unique 처리하여 멱등성 보장하고,  
발송이 폭주하면 슬라이딩 윈도우 등을 사용하여 보내는 양을 조절 + 워커 수평 증설   

푸시 발송 후 응답을 보고 실패 판단.  
지수 백오프로 시도 혹은 별도 큐에 보관  
<br>
<br>
<br>

**사용자 대시보드: 원장**  
주문이 체결되면 => 예수금 차감, 주식 보유 수량 보여주는 서비스  
체결 이벤트는 (외부?) 브로커로 전달받는데 중복 + 유실 + 순서 뒤바뀜 가능  

기록되는 시점부터 중복/누락을 통제해야 하는게 이 문제의 핵심  
외부 브로커에서 오는 만큼.. 체결 메시지는 seq가 있을 것임. 만약 건너뛸 경우 seq에 gap이 발생하니  
보류 + 브로커에 재요청 하는 방식이 좋을 듯.  

멱등성도 보장되어야 함(중복 x): 체결 ID를 unique하게 한 다음, 이를 write 할 때
예수금/보유 수 변경을 단일 트랜잭션으로 묶도록 하면 될 듯.  

그 외에 대사(Reconciliation)을 수행 => 외부 증권사 등으로 부터 체결 내용 보고 검증  
<br>
<br>

**사용자 대시보드: 원장 - 대사**  
대조할 내용(외부 브로커 체결 내역) vs 사용자의 원장  

흐름은 보통 이런 식이다: 수신 + 적재(스테이징) => 비교 => 불일치 세분화 => 재검증 => 확정 및 기록  
이를 단계별 그리고 청크별로 묶을 필요가 있다: 중간에 빠꾸 났을 때: 체크포인트  

체크섬, 파일ID 기반 중복 방지.  
비교비용은 먼저 사용자/계좌 별 합 + 체결 건수(길이) 비교  
이둘 중 하나라도 다르면 상세 정보 체결 내역 등을 비교  
여기서! 파일 누락(늦게 옴)이 발견될 경우 대사 단계로 넘어가지 않도록 하는 것도 중요.  

누락과 같은 명확한 유형만 자동 보정하고 나머지는 사람이 검토하도록.  
<br>
<br>

**사용자 대시보드: 원장 - 마이그레이션**  
서비스가 "중단 되지 않게" 교체를 하는 것이 목표이다.  
당연, 점진적 교체: 하나하나 서비스 기능 단위로 교체를 해야 한다.
섀도우 런닝: 해당 단위로 입력은 오지만 응답은 사용자에게 전달하지 않고, 내부적으로 대조한다.  

중단 되지 않는 만큼: 기존 데이터 옮기기 + 새로운 변동 내역 반영이 동시에 되야 함.  
CDC(Change Data Capture)를 사용해서 반영하면 됨.  

스냅샷도 필요. 먼저 기존 스냅샷을 찍고, 이후 변경된 CDC를 빠짐없이 기록, 순차적 반영.  
At-least-once · 멱등성 · Kafka 파티션 · 동시성 제어. 도 보장 필요.  
<br>
<br>

**사용자 대시보드: 인기 종목**  
거래소 피드 => Kafka => Redis => SSE  
SSE 선택 이유: WebSocket에 비해 비용이 저렴, 데이터 특성 상 서버 => 클라 방향이기 때문.  
다만 Stateful이어야 함: 사용자(클라)가 어떤 종목을 구독했는지, 또 클라와 지속적 연결 필요.  

증설 방식은? 종목별로 시세 데이터를 분산 ... 여러 SEE Gateway가 필요 종목 수집 => 발송  
재접속? `Latest-Event-ID`가 아닌, 스냅샷을 주면 됨. Seq 붙여서 순서 파악하고.  
왜 스냅샷인가? 매번 받은 피드를 실시간 반영 x: 0.1-0.2초 단위 스냅샷 제공.  
<br>
<br>

**사용자 대시보드: 내 자산**  
문제는 국내 주식 vs 해외 주식이 각각 다른 서버에서 수행을 하고 있고 이를 합쳐서 보여줘야 함.  

BFF(Backend For Frontend)라 해가지고.. 화면 전용 API를 만든다.  
이 녀석은 국내/해외 주식 서버의 API로 데이터를 각각 긁어오는 방식.  
요청 시 바로 => 실시간성이 뛰어나나, 한쪽이라도 빠꾸가 나면 서비스 전체 장애가 온다.  

CQRS(Command Query Responsibility Segregation)도 있는데,  
비동기적으로 두 서버에서 긁어오고 스냅샷으로 저장하고 있다가 사용자 요청이 오면 그때 보여줌.  
안정성이 높다: 한 쪽이 실패하면 display 안하거나, 과거임을 명시하고 보여주고,  
합계 산출 같은 것은 제한하는 방법.  
<br>

이런 방식은 여러모로 리스크 있음: <u>단일 장애점</u>이라 해가지고.. 여기가 문제 생기면  
윗 단계가 다 문제.  
<br>
<br>
<br>

**서비스 장애: 호가창**  
Redis가 죽으면 DB로 대규모 트래픽이 몰려옴. 서버에 부하가 오니, "서킷 브레이커"를 하는 방향  
으로 고려하는 게 좋음. 서버 내 로컬 캐시를 임시 대응책(Fallback)으로 만들고, 지연 등 명시.  

이후 새 Redis가 등장 기존 Redis 데이터를 복제했다고 해도..  
TTL 만료 => 캐시 스탬피드가 발생 가능. 사전에 워밍업을 하거나, singleflight 하도록 처리.  

현재가는 다음 값이 덮어쓰면 되므로 문제가 없으나, seq가 중요한 데이터가 있음.  
호가창은 최신 스냅샷 기준으로 복구, 이후 발생한 증분 이벤트(delta)를 반영.  
<br>
<br>

**서비스 장애: 원인 탐색하기**  
완화 먼저: 최근 변경 시점 이후로 문제가 발생한 것이라면, 롤백을 먼저 시행한다.  

원인을 좁혀가는 순서: 먼저 Grafana 등으로 API의 실패율 등을 살펴본다.  
여기서 유독 튀는 지표가 있다면, Jeager/Tempo를 통해서 구간 별로 어디서 병목이 생기는 지 파악.  

해당 서비스 상세 지점을 파악한다. GC Pause에 이상 지표가 보이는지, thread dump에서 스레드 풀  
상태 비중이 튀는지, 커넥션 풀, CPU/메모리 사용량 등 물리적인 지표도 확인한다.  

가설 => 검증 => 조치하는 방식으로 원인을 제거한다.
