#### 설명 중심으로  

`REPEATABLE READ`격리에서 나타나는 문제:  
각각 다른 버전의 Read View를 첫 트랜잭션에서 가지고 있다.  
그걸 기준으로 수행이 되기 때문에.. Lost Update가능.  

근본적인 문제는 읽기 + 쓰기 가 분리되어 있기 때문: **원자적 연산**을 하지 못함!    
`조건부 UPDATE`를 해서 하나의 쿼리문으로 "검사 => 집행"을 하는 방법으로 해결 가능.  

그 외에.. 비관적 락(`SELECT FOR UPDATE`)을 통해서 "읽기" 순간 부터 잠글 수 있음: 비관적 락  
version 칼럼을 사용해서 실패하면 롤백: 낙관적 락  
무식하게 직렬화도 가능함.  
<br>

Kafka에서는 파티션 별로 순서를 보장: accountId 기반 파티션 생성  
그래도.. 순서가 깨질 수 있다: 예를 들어 "컨슈머가 병렬 처리" 받는 쪽이 순서를 뒤바뀌면 가능  
그 외에, 실패로 인해 프로듀서가 재전송 할 때 꼬일 수 있음.  

멱등 프로듀서를 넣으면? => 순서가 유지. 다시 순차적으로 보냄(`enable.idempotence=true`)  
다중 파티션으로 병렬 처리? => 순서 조정하는 계층이 별도 필요  
<br>

`at-least-once` <=> `at-most-once`차이  
전자: 메시지 처리 → 오프셋 커밋 순서.. 중간에 죽으면 중복 발송.  
컨슈머 측에서 eventId를 unique 처리하여 멱등성 보장해야 함.  

반대로 프로듀서 측에서는 이런 순서 보다는 dual write를 묶을 수 있는  
**Transactional Outbox**를 구성할 필요가 있음.  
<br>

리틀의 법칙: 100건 × 3초 = 동시에 300건. Tomcat 최대 스레드 200개.. 스레드 풀 고갈 우려  
연쇄 장애 방지 위해 => **벌크헤드**로 격리 필요.  
그 외에 응답이 늦은게 장애일 경우 서킷 브레이커를 하거네 페일오버로 대체 채널을 찾기.  
<br>

데드락: 상호 배제, 비선점, 점유와 대기, 순환 대기.. 4가지 암기? 필요성 있음.  
계좌 중 작은 쪽을 먼저 항상 락을 획득하도록 해, 순환 대기를 깨도록 함. => 처음부터 대기하도록  
<br>

`double` <=> `BigDecimal`차이 이해 필요. 특히 소수점 계산 할 때는.  
`compareTo()`는 값 크기를 비교, `equal()`은 데이터 자체를 비교.  
<br>

p99가 주기적으로 튀는 이유 분석하기:  
GC Pause => JVM이 실행 일시 중단.. 사실상 지연  
DB 커넥션 풀 대기 => 요청이 지연되는 것: DB 접근 요청이    
스레드 풀 큐잉 => 요청이 지연되는 것: 스레드 사용 요청이  
CPU throttling => 정해진 할당량 초과 발생  
Thread Dump => `RUNNABLE`, `BLOCKED`(락 대기), `WAITING` 등으로 파악  
<br>

Dirty read => 트랜잭션 중간에 읽음  
Non-repeatable read => 새 read view 매번 보면서 값 변경, 일정치 않음  
Phantom read => 위와 비슷하게 변경되나 "새 값이 중간에 삽입"됨.  

MVCC(Multi-Version Concurrency Control: 다중 버전 동시성 제어):  
Repeatable read에서 특정 시점 view를 계속 보게 해도 만족하지 않나?  
=> MVCC가 기반(여러 버전의 view 생성)이 되고 이를 활용: non-repeatable read도 이를 활용
