**문제 01**  
> 주식장 개장 => TPS(Transaction Per Second)이 20배 폭증 가정 + 예약주문 100만건 외부 브로커로  
> 외부 브로커 상황: TPS 상한 존재, 응답이 수 초 느려짐  
> 유실과 중복 방지가 되어야 함  

여기서 말하는 외부 브로커를 이해하려면 다음과 같은 흐름을 이해할 필요가 있다:  
사실 아래가 기본 설계, 답의 일부이긴 하다.ㅎㅎ  
```
고객 100만 건 예약주문 + TPS 20배 폭증
         │
         ▼
토스증권 주문 서버
         │
         ▼
Kafka (내부 주문 대기열)
         │
         ▼
주문 전송 Worker
         │
         │ 외부 API 요청
         ▼
외부 브로커 서버
(해외 증권사·중개기관)
         │
         ▼
미국 주식 거래소
(NASDAQ, NYSE 등)
```
여기서 외부 브로커는 실제 접수에 성공/실패 여부(주문 접수 결과)를 주거나 응답 없음(Time out)인  
상황을 가정해야 한다. Timeout은 토스 쪽 서버에서 결정하는 것, 외부 브로커의 결과는 알 수 없으니..  
<br>

무엇을 해야 할까?  
먼저 **유량 제어**를 해야 한다. 외부 브로커 상한 이하로 보내야 하기 때문..  
위의 도식화의 `Worker`에 Rate Limiter를 설정을 하면 된다.  
만약 `Worker`가 여러 개라면? => 분산 Rate Limiter 등을 통해 전체의 속도를 조절해야 함.  

다음은 **예약 주문/실시간 주문 분리**이다.  
만약 단일 FIFO 큐(Kafka)라면 예약 주문을 처리하느라 실시간 주문이 오래 대기할 수 있기 때문..  
그럼 분리는 어떻게? => 주문 서버 + Kafka + Worker 모두 분리가 가능하다. 다음 아래 도식화 참고:  
```
                  주문 서버
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       예약주문               실시간 주문
          │                     │
          ▼                     ▼
 Kafka Topic A           Kafka Topic B
 (reserved-orders)       (realtime-orders)
          │                     │
          ▼                     ▼
    예약주문 Worker         실시간 Worker
    전용 스레드 풀          전용 스레드 풀
          │                     │
          └──────────┬──────────┘
                     ▼
              공통 Rate Limiter
                     │
                     ▼
                 외부 브로커
```
주의할 점은 공통 Rate Limiter임.  
<br>

마지막으로는 **장애 감지와 대응**이 있겠다.  
외부 브로커가 응답하지 못함=주문 실패.가 아니다. Timeout시 UNKNOWN으로 처리한 다음,  
실패율을 측정한다. 실패율이 특정 임계치를 넘으면 => 서킷 브레이커 or 서브 브로커로 Failover함  

서킷 브레이커(Circuit Breaker): 기존 브로커 대한 호출을 차단~재시도 하는 패턴  
서브 브로커(Sub Broker): 기존 브로커가 장애일 때 대용으로 쓰는 예비 브로커  

실시간 주문은 "실패했습니다(서버 장애)"로 사용자에게 보내고 끝날 수 있으나,  
예약 주문은 사실상 모두 보내야 한다. 실패 시 내구성 있는 저장소에 보관하고, 실패 확정 or 재시도

**문제 02**  
> 금융 원장 서비스(Ledger: 예수금, 보유 수량 갱신) 설계  
> 거래 체결 시 => 중복, 순서 바뀜, 누락 발생 가능.. 이를 대비한 설계 필요  

Append-only: 내부 기록을 보존한다. 설마 오류라 해도.. 다만, 사용자에게 보여지는 것  
ex. 입출금 내역. 같은 거라면 그대로 노출하지 않는다.  

잔고는 스냅샷으로: 만약 `SELECT SUM(amount).. WHERE ..;`식이라면, 매번 계산을 해야 하니,  
"특정 시점의 상태를 그대로 복사한 것(스냅샷)이 필요".  
<br>

오류(중복/뒤바뀜/누락)은 어떻게 처리?  
문제에 Kafka라고 쓰여져 있지 않은 만큼, 또 "원장 서비스"인 만큼 좁은 가정을 하지 말아야 한다.  
```
외부 거래소 / 브로커
        │
        ▼
체결 이벤트 전달 시스템
        │
        │ 중복·역순·누락 가능
        ▼
┌──────────────────────────┐
│      원장 서비스           │ ← 설계 대상
│                          │
│ ① 중복 이벤트 식별         │
│ ② 이벤트 순서 검증         │
│ ③ 누락 이벤트 감지         │
│ ④ 예수금·보유 수량 갱신     │
│ ⑤ 원장 정합성 검증         │
└──────────────────────────┘
        │
        ▼
     원장 DB
```
중복 처리: 체결 변호를 unique key로 하여 원장에 넣고, 잔고 갱신과 단일 트랜잭션으로 묶기.  
동시성: 같은 계좌에서 체결, 출금이 동시에 올 수 있음 => 조건부 UPDATE or 행 락하기.  
순서: Kafka의 계좌 당 파티션 할당하여 순서 보장, 원장 측에서 Seq 검사 => 늦게 온 앞 seq 반영.  
누락: 받아오는 Seq 번호를 기준으로 하여 gap(+2 이상 점프) 발생 시, 반영 중단 and 재전송 요청.

**문제 03**  
> 인기종목 아키텍처 설계(거래소 시세 => 앱 화면 갱신까지)  
> 메시지 양, 느린 클라이언트, 서버 증설, 재접속 까지 다루기.  

일단 거대한 흐름은:  
거래소 => 수신 서버 => Kafka => Redis에 유지 => WebSocket 혹은 SSE으로 사용자에게 전달  
SSE(Sever-Sent Events): 클라이언트 요청이 아닌 서버 측에서 실시간으로 전송을 함.  

전송 단위는 어떻게?  
사람 눈에 실시간으로 보여지는 것은 초당 여러 번이면 충분.. 즉 100 - 200ms에 한번 (1,000ms=1초)  
전송량을 계산하자면.. 초당 5번 × 10만명 = 50만 메시지를 보내면 됨: Throttling(전송 빈도 제한)    
100 - 200ms에 한번 => 스냅샷으로 찍어둔 다음.. 전송 시점이 아닌 접속자는 바로 이전 스냅샷 보여줌.  
```
거래소 → 시세 서버 → WebSocket 서버 → 사용자
          초당 30회      초당 5~10회
          원본 수신       100~200ms 간격
                             최신 값만 전송
```
<br>

송신 버퍼(Send Buffer):  
서버가 사용자에게 보내려는 데이터를 임시로 쌓아둠 => 느린 클라이언트일 수록 서버 메모리 고갈..   
<u>에초에 사용자가 늦으면, 지난 값들은 의마가 없어지므로</u> 버퍼 상한선을 두고, 오래된 시세 제거  

마지막.. 그럼 **증설**은 어떻게 하지?  
시세 수신 서버와 WebSocket 서버는 각각 용도가 다르다.. 보통 후자가 부하가 크고, 증설 필요성 높음  
시세 수신(Fan-in)은 정합성 중시, 시세 발신(Fan-out)은 수평 확장이 중요.  

Stateful로 클라이언트 접속량을 측정한다(FD: 소켓 연결 식별자, 메모리, 네트워크 사용량)  
특정 임계가 넘었을 경우, 서버를 증설한다 => 신규 접속을 여기서 맡음.  

*짧게 알아가기*  
Stateful: 클라이언트의 상태를 서버가 저장함(ex. SYN 핸드셰이크).. Socket 통신도 포함.  
Stateless: 반대로 서버가 보존 안함. UDP 통신을 생각하면 될 듯.  
<br>

전반적 흐름 도식화:  
```
증권사 / 거래소
       │
       ▼
  시세 수신 서버
       │
       ▼
  메시지 브로커 ← 여기!
  (Kafka / Redis Pub/Sub)
       │
       ├─────────────┐
       ▼             ▼
  Gateway A      Gateway B
  (WebSocket)    (WebSocket)
       │             │
       ▼             ▼
    사용자들        사용자들
```

**문제 04**  
> 자정이 다 되어감, 30분 전 주문 서버 배포 함 
> => p99가 200ms에서 4초로 늘어남 + 주문 API 실패율 알람.. 해결 과정 시나리오 생각하기  

*extra. 원인 파악보다 완화가 먼저 => 최근 변경 후 장애 발생한다면 일단 롤백을 한다*  

Phase 1. 병목(장애) 지점을 찾는 과정을 밟는다.  
장애 범위와 심각도를 파악해야 한다. 왜?.. 어디냐에 따라서 원인 후보를 줄일 수 있다.  

예: 
주문 API만 장애 => 주문 관련 코드, 외부 주문 API 의심  
모든 API에 장애 => 공통 DB, 네트워크, 서버 자체의 CPU 등 의심  
새 버전에서만 장애 => 최근 변경 코드 의심  

어떻게 장애를 측정하고 찾나?  
Grafana라고 있다. <u>API 별 실패율과 응답시간</u>을 보고 API 단위로 추론 가능.  
이 지표에서 유독 튀는 API가 있으면, **Jaeger/Tempo**를 통해서 개별 요청이 어느 구간에서  
지연이 발생했는지 추적한다. 예: 주문 API(주문 서버 => Redis => DB => 응답 생성)  

<br>
Phase 2. 찾은 지점(서비스 상세)를 세부적으로 파악한다.  
thread dump: 특정 시점에 JVM 내부 모든 스레드의.. 스냅샷(Run. block. wait. timed_wait.)  
커넥션 풀: DB와 접속하기 위해 만들어진 커넥션 객체?들 => 사용 중, 유휴(idle), 대기 수를 통해  
GC Pause: 가비지 콜렉하기 위해 잠시 스레드 멈춤 => 빈도, 시간 등에서 튀는 것 확인 필요  
CPU/메모리 물리? 지표.. 도 확인해 본다.  
<br>

Phase 3. 조치를 취한다.  
즉각적인 조치(Mitigation): 위에서 말한 롤백, 트래픽 제한, 장애 Pod 격리 등이 있다.  
근본적인 조치(Remediation): 문제가 되는 코드 수정, 쿼리 개선 등 장애 원인을 제거.

**문제 05**  
> MSA 관련 문제이다.  
> 국내 주식(서버 + DB + API) and 해외 주식(서버 + DB + API) 형태인데,  
> 합쳐서 보여주는 "내 자산" 화면용 API가 있을 때를 가정.  
> 한 쪽이 장애 상황이 올 때 시나리오를 추론하고, 통합 계층의 risk 서술.  

먼저 가장 간결하게 설계도를 추상화 하면 다음과 같다:  
```
                 [사용자]
                    │
                    ▼
              GET /my-assets
                    │
                    ▼
             [통합 자산 API]
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
    [국내주식 서버]       [해외주식 서버]
          │                   │
          ▼                   ▼
       국내 DB              해외 DB
          │                   │
          └─────────┬─────────┘
                    ▼
            데이터 형식 통일
                    │
                    ▼
          평가금액·수익률 계산
                    │
                    ▼
               사용자 응답
```
여기서 통합 자산 API는 두 서버로부터 정보를 얻어온다.  
이 또한 설계 방식이 두 가지로 나눌 수 있는데..  

1. Aggregation Layer (BFF: Backend For Frontend) - 화면 구성을 위한 백엔드 구현  
     화면 구성이 목적인 만큼 "통합 API" 각각 <u>두 서버의 API를 호출</u> => 통합 및 계산 => 응답  
     => 비교적 단순한 구현, 하위 서버 장애에 직접 타격, 최신성 바로 반영  
<br>

2. CQRS 읽기 모델 - 미리 합쳐 놓음  
     ```
     국내주식 DB ──→ CDC/이벤트 ──┐
                              ├──→ 통합 읽기 DB
     해외주식 DB ──→ CDC/이벤트 ──┘
                                        ↑
                                        │
     사용자 요청 ──→ 통합 API ─────────────┘
     ```
     위의 도식화 처럼, <u>비동기적으로 데이터를 갱신</u>하는 구조.  
     CDC(Change Data Capture:데이터 변경 추적)이나 이벤트로 전달받아서 미리 미리 반영.  
     => 구현 복잡도는 높으나, 하위 서버 장애 시 덜 영향(기존 데이터 조회), 최선성 좀 떨어짐.  
<br>

*한쪽 서버가 장애일 때 => 장애 대응은 어떻게?*  
API에 Timeout을 설정.. 무한 대기를 방지, 반복 실패시 Circuit Breaker를 적용할 것.  
한쪽만 실패한다면 정상 데이터 부분만 불러오기: 통합 계산 결과는 display하지 않음.  
CQRS라면, 실패한 경우 이전 저장 데이터를 보여주되 "마지막 갱신 시간"을 보여주는 방법도 좋음.  
<br>  

*통합 계층 자체의 위험?*  
단일 장애점(SPOF: Sigle Point Of Failure)가 될 수 있다. 여러 요청들이 이 단일 지점을  
거쳐 가기 때문에.. CPU 포화/메모리 부족/스레드 풀 고갈.. 등 문제가 생기면 전부 찐빠.  

해결 방식은.. 아래 도식화 처럼:  
```
               [프론트엔드]
                     │
                     ▼
                [로드밸런서]
                 /       \
                ▼         ▼
         [통합 서버 A] [통합 서버 B]
                \         /
                 ▼       ▼
            [국내·해외 서버]
```
통합 서버 또한 여러 개를 두어서, 대비용으로 운영을 하는 방식도 좋겠다. 
그 외에도, 통합 계층에 비즈니스 로직 비대화 => 하위 계층과의 "의존성"이 증가하는 문제.  
<br>
<br>

**문제 06**  
> 원장 시스템을(레거시 => 새 것) 교체함.. 마이그레이션   
> 서비스 중단이 없어야 함 + 데이터 정합성 보장 필요  

일단 "그냥 옮긴다"는 과정을 차근차근 생각해보자. 테이블에 있는 데이터를 '그대로 복사'  
하는 과정은 비교적 간단하다. 그런데 <u>서비스를 멈추지 않는다는 조건</u>이 붙으면?  

즉, 데이터를 복사하는 동안 새로운 거래가 계속 발생하고, 이 또한 (신규 DB에) 집어넣어야 한다.  
복사 중에 발생한 변경 사항까지 신규 시스템에 전달 필요! => CDC/이벤트 기반 동기화  
```
[레거시 원장 DB] ─── 초기 데이터 복사 ───→ [신규 원장 DB]
       │                                       ▲
       └──── CDC / 변경 이벤트 지속 전달 ─────────┘
```
<br>

CDC(Chanage Data Capture)의 예시:  
`INSERT`, `UPDATE`, `DELETE` 감지 => 전송 => 신규 서버에 반영(ex. 잔액 100만원 => 90만원)  

이벤트 기반 동기화:  
레거시 서버가 거래 처리 => 이벤트 발행 => 신규 서버에 발행  
<br>

그런데? 이 과정에서 **정합성 문제**가 발생할 수 있다. 이전에 학습한 내용을 응용해서 활용 =>  
-. at-least-once: 유실 방지 목적으로 재전달 허용  
-. 멱등성: 재전달 이벤트 중복 반영하지 않도록  
-. Kafka 파티션: 동일 계과 이벤트 순서 보장  
-. 동시성: 여러 트랜잭션이 동일 계좌 동시 수정 방지(ex. SELECT FOR UPDATE)  
<br>

이후의 과정: Shadow Running(병행 검증) => Strangler Fig Pattern(점진적 전환)  
왜 Shadow(그림자)냐?.. 레거시 시스템으로 돌고, 여기 응답이 사용자에게 감.  
그러나 새 시스템은 동일 요청을 받고 응답은 가지 않되, <u>내부적으로 검증</u>을 수행.  

검증은 how? => 동일한 시퀀스(시점), 과거 거래 재션, 경계 조건 테스트(반올림 등)  
이렇게 통과한 부분은 "점진적", 그러니까 파트 하나하나씩 교체를 한다. 이것이 "점진적 전환"
