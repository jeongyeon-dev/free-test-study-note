#### 서버 성능·장애  

**문제 06**  
> 서버의 처리량을 계산하고 어떠한 문제가 발생할 지 시나리오 작성 && 대응책    
> Java의 Tomcat 환경(최대 스레드 200개) + 동기 호출 엔드포인트 초당 100건(평소)  
> 현재 현상: 50ms(평소) => 3초로 응답 지연  

현 아키텍처의 구성은 다음과 같이 추정 가능:  
```
사용자 앱 (초당 100건 요청)
        │
        │ POST /orders .. 엔드포인트(클라이언트의 요청)
        ▼
토스 서버 (Tomcat, 최대 200스레드)
        │
        │ 외부 API 동기 호출
        ▼
외부 증권 브로커 API
        │
        │ 평소 50ms → 현재 3초
        ▼
토스 서버에 응답
        │
        ▼
사용자 앱에 최종 응답
```
*Tomcat 200개는 Spring Boot 인스턴스 한 개의 최대 스레드 한도이다.* 

해당 서버의 평소 처리량 추측하기: 0.05초 × 100건 = 스레드 5개 점유.. 로 추측 가능.  
해당 서버의 장애시 필요한 스레드 수: 3초 × 100건 = 스레드 300개 필요.  

그런데?.. Tomcat은 스레드 한도가 200개로 고갈이 될 것으로 예측됨.  
=> 고갈되면, 현 서버의 다른 기능(ex. 잔고 조회, 시세)들도 지연 현상이 나타남: 연쇄장애.  
<br>

해결책?.. 은 크게 두 가지로 나눈다고 생각했으나..   
*스레드를 증설하는 방식?*:
현재 문제는 "외부 브로커의 지연"이지, <u>본 Spring 서버의 문제가 아니다</u>.  
Tomcat 스레드가 외부 브로커의 응답을 기다리는 동안 다른 HTTP 요청을 처리하는데 재사용 못하는 것.  
```
사용자 → Spring Boot 서버 → 외부 브로커
              │                 │
              │   응답 대기      │
              │◀────────────────│
              │                 │
         Tomcat 스레드 점유     3초 후 응답
```
<br>

*일정량까지만 처리하도록 해당 요청을 격리하는 방식*  
이것이 정답에 가깝다. 격리방식은? => Bulkhead(벌크헤드).. 특정 작업의 사용가능 자원 제한 + 격리  
그리고, Timeout.. 특정 시간 이상이 지나면, 호출 자체를 끊고 실패 처리하기.  
하나 더, Circuit Breaker(서킷 브레이커).. 장애 반복 시 외부 호출 제한/차단 => 이후 복구 흐름.  
마지막으로, failover(페일 오버).. 실패 수가 일정량 늘어나면 => 예비 서브 브로커를 사용.

**문제 14**  
> p50은 정상 p99만 "주기적"으로 튈 경우  
> 원인 후보 4개로 간추리기 & 추정하는 방법   

문제에서 API 기준으로 측정을 했다. 만약 페이지 하나를 그리는데 API 20개 필요하다면,  
p99에 걸릴 확률은 1 − 0.9920 ≈ 18% 가까이 된다. 하위 1%도 튀면 문제.  

측정할 수 있는 지표를 활용하자면..  
**GC(Garbage Collector) Pause**: 가비지를 수집하기 위해 잠시 서버가 멈춘다.  
```
시간       Spring 요청 처리           JVM GC
────────────────────────────────────────────
0ms        정상 처리
10ms       정상 처리
20ms       모든 Java 스레드 일시 정지 → GC 수행
80ms       요청 처리 재개              GC 일시 정지 종료
90ms       정상 처리
```
GC 로그에서 p99 스파이크 시점에 비정상 패턴을 찾아서 원인 후보를 간추릴 수 있다.  
.1 GC 빈도 급증 => 객체 생성량 증가 or 힙 메모리 압박 의심  
.2 GC 정지 시간 증가 => live 객체 증가 or 무거운 GC 작업 의심  
.3 GC 후에도 메모리 사용량 높음 => 메모리 노수 or 과도한 객체가 있는지 의심  
<br>

**HikariCP**: JDBC DataSource 구현체?.. Spring 서버와 DB와의 연결함  
이 커넥션(연결)을 풀(Pool)로 보관하고 있다가 쓰는 방식으로 운영된다. 확인할 지표로는,  
Pending: DB 커넥션 빌리려고 대기하는 스레드 수 => 급증 시 확보하지 못해 지연됨.  
커넥션 획득 시간: Pending에서 획득까지 걸린 시간 => 급증 시 마찬가지로 지연 원인.  
<br>

**Thread Dump**: 특정 시간을 기준으로 살아있는 스레드의 상태를 찍은 스냅샷(p99 시점에).  
Blocked 급증 => 여러 스레드가 락 얻으려고 경쟁: 락 경함 의심  
Waiting 다수 => 특정 작업 완료/자원 반환을 기다리는 상황: 호출 스택(현재 실행 함수들) 확인  
Timed_Waiting 다수 => 외부 응답, 타임아웃 등 대기 가능성: 호출 스택 마찬가지로 확인   
Runnable 다수 => CPU 연산 집중임: CPU 자원 부족 가능성 의심  
<br>

**CPU throttling**: 운영체제가 CPU 사용을 일시 제한  
왜? => 일정 시간 동안 사용할 분량(Quota)로 제한을 하기 때문. 초과 시 제한을 시킴.  
```
실제 시간     0ms        50ms       100ms
              │──────────│──────────│
CPU 사용      2코어 실행  실행 제한
CPU 시간      100ms 소진  다음 주기 대기
```
즉, 이 지표가 급증했다면 CPU 한도 때문에 요청 처리가 지연된 것을 의심할 수 있음. 
<br>

그 외에.. 주기적 작업으로 인해 지연 현상이 이 때 발생하는지, 그리고  
**Distributed Tracing(분산 추적)**이라 해가지고, 구간별로 나눠 지연 구간을 찾기.  
```
전체 API 응답 시간: 3,100ms

Controller 처리       10ms
Service 처리          20ms
외부 증권사 API 호출  3,000ms  ← 병목
DB 조회               70ms
```

#### 분산 시스템  

**문제 11**  
> CQRS(원본 DB와 읽기 전용 DB 분리) 상태  
> 매수 직후 => 보유 종목에 보이지 않음. 문제 발생.  

CQRS(Command Query Responsiblity Segregation)에서, 원본 => 읽기 뷰로 비동기적으로 CDC로    
전바가 진행된다. "전파 지연"이 일어나는 만큼, 최신의 것 읽기가 되지 않는 현상이다.  

이는 read-your-writes(내가 쓴 것은 내가 읽기) 원칙에 반하므로, 이를 해결하기 위해  
사용자의 읽기 요청을 원본에서 읽게 하는 방법이 있다.  

다른 방법으론, "사용자가 읽기 요청"을 보낼 때, 읽기 뷰의 버전과 원본 DB 버전 비교 => fallback    
<br>

*추가 복습/학습*  
CDC(Change Data Capture): DB에서 발생한 데이터 변화 감지  
이것을 원본 DB에서 감지 => 읽기 전용 DB에 반영(주기적으로)  

Fallback: 원래 사용하는 방법이 부적절/불가능해 다른 방법 사용하는 것  
평소에 읽기 DB에서 조회하나 버전이 오래된 경우 => 원본 DB에서 조회  

전파 지연 모니터링: 읽기 DB가 얼마나 뒤쳐졌는지 확인하는 것.

**문제 15**
> 브로커의 수용량, 예약 대기 건수 제시됨  
> 처리율 제한 알고리즘(고정 윈도우, 슬라이딩 윈도우, 토큰 버킷) 차이 이해 및 적용  

먼저, "브로커"에 대한 정의 부터 알기: 두 시스템 사이에서 "중계'하는 주체.  
해당 시스템이 내/외부이든 간에, 브로커를 통해 진입해야 하는 상황이다.  

예약 100만 건 ÷ 초당 2,000건(까지만) = 500초가 걸린다. 최소 8분 20초.  
!여기서 최대 2천 건이지, 알고리즘이나 환경에 따라 변동이 있을 수 있음!  
<br>

**처리율 제한(Rate Limiting) 알고리즘**: 트래픽 양을 제어 => 과부화 방지 and 안정성 유지 목적  
왜 제어하나?.. 서버 측에서는 초당 1만건 등 크게 보낼 수 있으나, 브로커에 맞게 속도조절 하는 것.  

*수도꼭지 물의 흐름을 조절하듯이 하는 것* 으로 이해하면 될 듯.  
<br>

-1. 고정 윈도우(Fixed Window)  
임의 설정 범위(ex. 1초) 간 허용하는 요청량을 제한하는 방식이다. 이는 시간에 따라 고정되어 있다:  
이렇게 할 경우 "카운트 경계"에서 몰리는 현상이 발생 가능: 경계 문제(Boundary Problem)이라 한다.  
```
0.99초에 2,000건 전송 → 첫 번째 구간 한도 충족
1.00초에 카운터 초기화
1.01초에 2,000건 전송 → 두 번째 구간 한도 충족
```
각 구간에서 2천건을 지켰으나, 0.02초 사이에 4천건이 몰리는 현상 발생.  
<br>

-2. 슬라이딩 윈도우(Sliding Window)  
고정 윈도우 처럼 시간이 딱딱. 맞는게 아니라, 현재 시간에서 1초(임의 설정)동안 전송 건 추적  
예: 현재 시간 `09시 43분 31.7초`라면 => `09시 43분 30.7초`까지 전송 건 추적 => 여분 전송 허용  

고정 윈도우에 비해 안정적이나, 요청이 발생할 때마다 검사를 해야하니 비용이 좀 듦.  
<br>

-3. 토큰 버킷(Token Bucket)  
전송 가능량을 "토큰"으로 환산해서 관리하는 방식. 위의 예시라면 초당 2천 토큰이 버킷에 쌓임.  
토큰이 없으면 => 충전 때까지 대기, 요청이 토큰을 얻으면 => 전송  

-4. 누출 버킷(Leaky Bucket)  
요청을 버킷에 쌓아두다가, 전송 허용량 만큼 졸졸.. 흘러보내는 것: 대기 큐와 유사.  
<br>

#### 캐시

**문제 09**  
> 캐시 TTL(Time-To-Live)이 만료되었을 때 시나리오를 가정  

문제에서 나타난 현상은 **캐시 스템피드(Cache Stampede: 캐시 쇄도)**이다.  
다수의 캐시가 유효 시간(TTL)이 한꺼번에 끝나면서 => DB 요청이 쇄도하는 현상 발생.  

*주관식 1페이지 참조할 것:*  

공유하는 Redis에 분산 락을 걸거나(여러 서버가 사용), singleflight로 한 요청만 읽고,  
나머지는 기다리다가 캐싱된 값을 읽도록 수행 => DB에는 해당 요청 당 1회만 접근.  
(분산 락 사용시: 그 락으로 보호되는 캐시 작업은 동시에 하나만 수행됨)  

TTL에 jitter(변동)를 넣어서 조금씩 만료 시간을 미세하게 차이나게 분산시킴.  

만료 전 캐시 갱신: 백그라운드(별도 스캐줄러 등)에서 만료시간 확인 후 갱신 진행.

#### JVM·메모리  

**문제 13**  
> JVM 프로세스 메모리 구조에 대한 이해 필요  
> JVM을 담는 컨테이너에 대한 이해 요구  

문제 전체를 요약하자면, JVM의 힙 메모리를 2GB로 한도를 늘렸는데, JVM을 감싼  
컨테이너 메모리가 2GB라서 한도 초과로 죽은 거다.  

그럼에도, JVM 경고인 `OutOfMemory`가 안나온 이유는, JVM 초과하기 전 컨테이너 쪽 초과로  
죽었기 때문.  

왜? => JVM에는 다음과 같은 구성요소가 있다(대표적으로)  
Heap: `new`로 생성한 객체를 저장하는 공간.  
Stack: 각 스레드의 메서드 호출, 지역 변수 저장하는 곳.  
Metaspace: 클라스 메타데이터를 저장.  
Direct Memory: 네트워크, 파일 I/O 등 효율적 처리에 연관.  

만약 Heap만 `-Xmx2g`명령어로 최대 크기를 2GB로 한다면, 총 JVM 크기는 이보다 커지는게 확정.  
=> 최대 한도 설정인 만큼, 한도 도달 전 까지는 컨테이너에서 정상 가동됨.  

Pod(컨테이너 감싸는 껍질)이 2GB이니, cgroup limit(리눅스 자원 제한 기능)를 초과하게 됨.  
리눅스 상 SIGKILL(강제 종료)가 이뤄지며, 137(sigkill로 인한 코드)를 내보내게 됨.  
```
JVM 자체 메모리 부족
Heap 한도 도달 -----→ OutOfMemoryError

JVM이 메모리 할당 실패를 감지하고 Java 오류를 발생시킴


컨테이너 메모리 부족 
cgroup 한도 초과 -----→ 커널 SIGKILL

운영체제가 프로세스를 강제 종료하므로 JVM의 예외 처리를 거치지 않음
```

#### 네트워크·통신  

**문제 08**  
> TIME_WAIT에 대한 개념 이해 및 해결 방법  
> TCP 통신에 대한 이해가 필요하다.  

TIME_WAIT은 TCP 통신이 종료할 때 나타나는 한 상태이다. 아래 도식화:  
```
[클라이언트]                     [서버]
ESTABLISHED                    ESTABLISHED
    |                              |
    | ----- FIN (seq=x) -------->  |
FIN_WAIT_1                         |
    |                              |
    |  <---- ACK (seq=y, ack=x+1)  |
FIN_WAIT_2                    CLOSE_WAIT
    |                              |
    |                     (남은 데이터 전송 완료)
    |                              |
    |  <---- FIN (seq=y) -------   |
    |                        LAST_ACK
    |                              |
    | ----- ACK (ack=y+1) ------>  |
TIME_WAIT                     CLOSED
    |                              |
(2MSL 타임아웃)                     |
    |                              |
CLOSED                             |
```
TIME_WAIT를 하는 이유:  
지연 패킷을 마저 기다리기 위해 => 도착 못하고 새 연결이 만들어 졌을 떄, 섞일 수 있음.   
정상 종료 보장(마지막 ACK 보내기 위해 => 이게 유실된 상태에서 "닫아"버리면, 상대는 걍 기다림)  
<br>

그런데? 이 TIME_WAIT 기간은 꽤 길다(ex. 60초) 만약 초당 1,000의 소켓이 열리고 닫으면  
6만개의 종료 소켓이 누적된다. => 고갈(TIME_WAIT이 끝나야 소캣 생성 자리가 생김)  

해결방법? => **HTTP keep-alive**와 커넥션 풀을 사용: 요청마다 닫지 말고 소켓을 재사용 함.   
이럴 경우 3-way-handshake 같은 비용도 사라진다는 장점이 있음.

**문제 12**  
> 실시간 시세 정보 => 클라이언트에게 보내기  
> polling, long polling, SSE(Server Sent Event), WebSocket 비교 및 이해 필요.  

먼저.. Polling(폴링)이란 무엇인가?.. 우리가 흔히 아는 요청 => 응답 흐름을 의미하나,  
좀 다른 점이 클라이언트 쪽에서 "주기적"으로 요청을 한다: 일반적인 HTTP랑 다름    

Long Polling은 클라이언트가 요청한다고 바로 보내는 것이 아닌, 새로운 데이터가 없다면,  
서버가 보류하다가.. 생성된 후 보낸다.  
=> 데이터 변화가 느리다면?.. 중복 요청을 무시하게 되므로 Long Polling이 서버 부담 down.  

WebSocket은 양방향 통신, 데이터 변화 시.. 서버 측에서 => 먼저 데이터를 보냄.  
SSE는 단방향 통신인데 서버 => 클라. 방향만 가능. 대신 클라이언트 측에서 이를 "요청"할 때만!  
<br>

주식 시세 같은 것은 굳이 클라이언트 측에서 뭘 건넬 필요가 없고, 일방적인 정보 받기이니,  
SSE가 적합하다고 할 수 있다. WebSocke은 별도 프로토콜, 연결을 관리해야 하니 비용 up.

#### 금액 정밀도

**문제 10**  
> 금액 정밀도에 대한 문제이다. Java의 double 속성에 대한 질문이기도 하다.  

double은 2의 거듭제곱을 조합해서 표현한다:  
```
0.5    = 1/2
0.25   = 1/4
0.125  = 1/8
0.0625 = 1/16
```
이러한 방식은 <u>정수 부분에서는 문제가 없으나 소수점에서 문제가 발생</u>한다.  
예를 들어 소수점 0.1은 근사값으로 저장되는 식.  
<br>

반대로 BigDecimal은 정수와 10의 거듭제곱을 이용해서 표현한다.  
```
0.1   = 1 × 10⁻¹
0.25  = 25 × 10⁻²
0.123 = 123 × 10⁻³
```
따라서 물리적인 저장 방식도: 정수 + 소수 자릿수로 표현이 된다.  
그래서 소수 연산에서 정확성 보장.  
<br>

환율 등을 계산할 땐, 금융사와 거래·정산 규칙에 따라 소수점 자릿수, 반올림을 시행  
화면 표시 기준은 "굳이 따를 필요가 없다" => 가독성 고려해서 자릿수 생략 & 반올림 가능
