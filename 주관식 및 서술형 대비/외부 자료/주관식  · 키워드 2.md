#### 시스템 성능·가용성  

**리틀의 법칙(Little's Law)**  
식은 다음과 같다: `L = λW`  

시스템 안의 평균 요청 수(동시 존재) = 도착률(시간 당) × 평균 체류 시간. 으로 계산을 한다. 예시로,  
한 시간에 10명이 방문, 평균 0.5시간 식사를 한다고 가정할 경우  
=> 10 × 0.5 = 5명.. 즉, 식당 내 동시에 존재하는 손님 수는 5명이다.  
```
손님
 ↑
10│                              손님10 ──────────────
 9│                           손님9 ──────────────
 8│                        손님8 ──────────────
 7│                     손님7 ──────────────
 6│                  손님6 ──────────────
 5│               손님5 ──────────────
 4│            손님4 ──────────────
 3│         손님3 ──────────────
 2│      손님2 ──────────────
 1│   손님1 ──────────────
  │
  └──────────────────────────────────────────────────→ 시간
      0    6   12   18   24   30   36   42   48   54   60분
```


이걸 초 단위, 컴퓨터 기준으로 해보자:  
초당 100건 => 요청 수, 평균 3초 => 머무는 시간.. 계산 시,  
=> 100 × 3 = 300개의 요청이 동시에 존재한다.

**서킷 브레이커(Circuit Breaker)**  
외부 호출의 실패율 임계치 초과 => 호출을 일시적으로 차단하는 것.  
이후 백업본 사용하거나, 서브 브로커 사용을 하던지 방법이 있으나, 이는 서킷 브레이커 범주 x.  

서킷 브레이커 상태는 다음과 같다:  
CLOSED: 정상적으로 호출되고 있음, 실패율 모니터링 중.  
OPEN: 실패율 임계 초과, 호출을 차단하고 실패 처리 반환.  
HALF-OPEN: 일부 호출을 복구해서 시도하기.  

이후 대안을 찾아 실행하는 것은 **Fallback**이라 한다.  
또한, 장애가 발생한 시스템을 다른 정상적인 걸로 전환 => Failover라고 함.  

!문제에서는 "외부" 호출이라고 했으나, 내/외부 모두 가능하다!  
<br>  

이런 장애에 대한 대응으로 **Bulkhead(벌크헤드)**가 있다.  
배 내부의 '칸막이'를 생각하면 됨. 물이 차도 다른 쪽까지 퍼지지 않도록.  

ex.  
만약 여러 서비스가 공유해서 사용하는 "스레드 풀"이 있다고 쳐보자.  
장애 서비스가 이를 다 점유하기 시작하면, 타 서비스에도 연쇄적으로 장애가 퍼진다.  
따라서, 장애 서비스 전용 스레드 풀을 만들던지, 격리 조치를 수행해야 함.  
<br>
<br>

리틀의 법칙 활용해보기  
예약주문 1,000,000건: 100만건 / 초당 2,000건 한도로 보낸다면?.. 머무는 시간(채류율) 없음.  
동시 존재 수 = 2,000 × ? 이므로 계산 불가!  

다만 예약 주문 수/초당 소비 수 = 총 걸리는 시간(초)가 나온다. => 500초: 약 8분 20초이다.  
여유 마진을 20%로(1,600TPS)로 설정하여 계산도 가능하다.  
<br>

윈도우 => 브로커의 수용량(ex. 초당 1천 건)에 맞춰 요청을 전송하는 "처리율 제한"이다.  

고정 윈도우: 고정된 시간을 간격으로 둠 => 최대 ×2배의 처리를 할 수 있다.. 과부하 위험.  
슬라이딩 윈도우: 요청이 올 때, 요청 시점 ~ 이 전 시간 간격 사이를 잼 => 안정적이나 리소스 필요.  

그 외에 "토큰 버킷"과 "누출 버킷"이 있다.

#### 동시성·멱등성·캐시  

**멱등성(idempotency)**: 같은 요청/이벤트를 보내도 한 번 처리한 것과 동일.  

카프카 => 컨슈머 흐름에서 "at-least-once(최소)" 한 번은 보내는 방식을 할 때(유실 방지)  
중복을 막기 위해 컨슈머에 멱등성 처리가 필요.  

그 외에 "at-most-once"가 있고, "exactly-once"가 있다.  

공부했는데 헷깔리는 점: at-least/most-once는 어느 설정에서 이를 결정하나?  
=> Offset을 언제 커밋하냐가 중요: 처리(ex. DB에 insert)를 분기로 하여.  
<br>

**데드락 4가지 조건**:  
상호 배제 => 하나의 락은 동시에 한 트랜잭션만 소유.    
비선점 => 락 강제로 뺐을 수 없음. 
점유와 대기 => 점유한 상태에서 상대 자원을 기다림.   
순환 대기 => 서로 상대방의 락을 기다리는 순환 구조  

다음 아래와 같은 방식(계좌ID 작은 쪽 부터 잡기)이면.. 4가지 중 "순환 대기"를 할 필요가 없어 진다.  
```
T1: A 락 획득 → B 락 획득 → 이체 → 락 해제
T2: A 락 대기 → A 락 획득 → B 락 획득 → 이체
```
<br>

#### 네트워크·실시간 통신  

**TIME_WAIT**: TCP 통신에서 연결을 끊을 때 4-way-handshake 발생.  
여기서 종료하고자 하는 측이 마지막에 `TIME_WAIT`을 `2MSL`간 유지.  
왜? => 마지막 ACK이 손실 가능성을 염두해 둠 + 망 중간에 데이터가 다 들어올 때 까지.  
<br>

19번 문제는.. 너무 지엽적이다. 스킵.  
<br>

**SSE(Server Side Event)**에 대한 지엽적 지식을 알아야 할 듯.  
Last-Event-ID: 마지막으로 받은 이벤트가 무엇인지 클라이언트 측에서 저장. 예시:  
```
서버 → 클라이언트

이벤트 ID 1 전송 → 수신 성공
이벤트 ID 2 전송 → 수신 성공
이벤트 ID 3 전송 → 수신 성공

--- 연결 끊김 ---

이벤트 ID 4 발생
이벤트 ID 5 발생

--- 재연결 ---

클라이언트 → 서버
Last-Event-ID: 3

서버 → 클라이언트
이벤트 ID 4, 5 재전송
```

#### Java·알고리즘·자료구조

`System.out.println( ? + ?)`같은 걸 할 때, 안의 `?`에 정수가 들어가면 `int`형,  
소수가 들어가면 `double`형이 된다. 

*안정 정렬*..  값이 같은 데이터 둘이 A, B 순일 때, 정렬 진행 후에도 A, B 순이면 안정 정렬임.  

객체 배열(Integer[], List)  
=> 같은 값 끼리 순서 유지가 중요: 객체 내 다른 요소들이 꼬이면 X.
```
class Student {
    String name;
    int score;
}
```
=> 안정 정렬인 TimSort를 사용한다. 시간복잡도: O(n log n)  
<br>

반대로 기본형 배열(int[], double[])은,  
얘네들만 바꾸면 되니까 안정 정렬을 굳이 사용하진 않음. Dual-Pivot QuickSort을 사용.  
<br>
<br>
자료구조와 시간복잡도:  
PriorityQueue(우선순위 큐) => O(log n).. 삽입, 삭제시 모두
